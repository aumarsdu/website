## 3. 每批的实际动作

1. **核验**：确认 Git 根/分支/相关 diff、适用 AGENTS、源与 Spec/Plan 哈希、候选目标及进程/文件归属。旧工作区脏文件保留。可用 `git status` 等只读命令；远程 PR/CI 只在本地候选实施确实依赖时才查，不让无关远程状态阻断本地工作。
2. **选 READY**：根据账本依赖重算 DAG，只领取一个任务为 Writer。若 T01 review 仍未完成，先修复上一轮可由 AI 自行解决的四项缺口，整理精确审查包；剩余独立判断标 `WAITING_OWNER`。不通过降低 G-R 来解锁 T02。
3. **实施与最窄测试**：使用隔离目录和候选数据根；先写或冻结反例/golden，再修改代码，运行相关单元、目标 PostgreSQL 集成、lint/format/type 检查。发现新失败按来源分类，不隐藏。
4. **批次验收**：按原 Spec 逐项记录 PASS/FAIL/NOT_RUN 与证据。真实 OCR/页面 golden 必须由未实现该候选者审核；无可用复核者时进入 `WAITING_OWNER`。候选迁移/发布器/规则也按 G-R 处理。
5. **回读与更新**：每任务/批次更新 `task_state.json`、证据索引和必要文档；为新版本重新计算哈希，回读最终 diff。只把已验收任务标 DONE；依赖解锁后把后继从 BLOCKED 重新评估为 READY。
6. **继续或停止**：有 READY 且非高危工作就持续下一批。若等待的是具体 Owner 业务规则、独立金标准或高危操作授权，只停受影响分支；若无其他 READY，留下可审查状态和唯一下一决策。未知提交回执先核查，不能重试碰碰运气。
